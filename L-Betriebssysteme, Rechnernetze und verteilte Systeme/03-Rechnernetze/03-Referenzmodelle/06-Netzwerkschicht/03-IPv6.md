# IPv6 - Internet Protocol Version 6

## Definition

> [!quote] Definition
> **IPv6** ist die aktuelle Version des Internet Protocols mit 128-Bit-Adressen, entwickelt als Nachfolger von IPv4 zur Lösung des Adressmangels und zur Vereinfachung des Protokolls.
## Motivation für IPv6

### IPv4-Erschöpfung

![[ipv4-adressraum-erschoepfung.png]]
*<span class="fig-id">03-03-06-ipv4-adressraum-erschoepfung</span>: Der IPv4-Adressraum mit ca. 4,3 Milliarden Adressen ist nahezu vollständig vergeben.*

### Vergleich IPv4 vs. IPv6

| Eigenschaft | IPv4 | IPv6 |
|-------------|------|------|
| **Adresslänge** | 32 Bit | 128 Bit |
| **Adressraum** | ~4,3 Milliarden | ~340 Sextillionen |
| **Header-Länge** | 20-60 Bytes | 40 Bytes (fix) |
| **Fragmentierung** | Router & Hosts | Nur Quell-Host |
| **Checksum** | Im Header | Entfernt |
| **ARP** | Separates Protokoll | NDP (ICMPv6) |
| **Broadcast** | Ja | Nein (Multicast) |
| **IPsec** | Optional | Integriert |

## IPv6-Adressformat

### Struktur

Eine IPv6-Adresse besteht aus **128 Bit**, dargestellt als 8 Gruppen hexadezimaler Zahlen:

![[ipv6-adressstruktur.png]]
*<span class="fig-id">03-03-06-ipv6-adressstruktur</span>: Aufbau einer IPv6-Adresse mit Netzwerk-Präfix (64 Bit) und Interface Identifier (64 Bit).*

### Kurzschreibweisen

**Regel 1:** Führende Nullen in einem Block weglassen
```
2001:0db8:0000:0042 → 2001:db8:0:42
```

**Regel 2:** Eine Folge von Null-Blöcken durch `::` ersetzen (nur einmal!)
```
2001:0db8:0000:0000:0000:0000:0000:0001
     ↓
2001:db8::1
```

**Beispiele:**
```
fe80:0000:0000:0000:0000:0000:0000:0001  →  fe80::1
2001:0db8:0000:0000:0000:ff00:0042:8329  →  2001:db8::ff00:42:8329
0000:0000:0000:0000:0000:0000:0000:0001  →  ::1 (Loopback)
0000:0000:0000:0000:0000:0000:0000:0000  →  :: (Unspecified)
```

> [!warning] Wichtig
> `::` darf nur **einmal** pro Adresse verwendet werden, da sonst die Anzahl der Null-Blöcke nicht eindeutig bestimmbar ist.

## IPv6-Header

Der IPv6-Header ist **immer 40 Bytes** lang (vereinfacht gegenüber IPv4).

### Header-Felder

| Feld | Bits | Beschreibung |
|------|------|--------------|
| **Version** | 4 | IP-Version (6) |
| **Traffic Class** | 8 | QoS-Markierung (wie DSCP) |
| **Flow Label** | 20 | Kennzeichnung zusammengehöriger Pakete |
| **Payload Length** | 16 | Länge der Nutzdaten |
| **Next Header** | 8 | Typ des nächsten Headers |
| **Hop Limit** | 8 | Entspricht TTL bei IPv4 |
| **Source Address** | 128 | Quelladresse |
| **Destination Address** | 128 | Zieladresse |

## Header-Vergleich: IPv4 vs. IPv6

Die folgende Gegenüberstellung zeigt die strukturellen Unterschiede beider Header:

![[ipv4-ipv6-header-vergleich.png]]
*<span class="fig-id">03-03-06-ipv4-ipv6-header-vergleich</span>: Strukturvergleich von IPv4- und IPv6-Header mit entfernten und neuen Feldern.*

### Detaillierter Feldvergleich

| IPv4-Feld | IPv6-Entsprechung | Änderung |
|-----------|-------------------|----------|
| **Version** (4 Bit) | **Version** (4 Bit) | 4 → 6 |
| **IHL** (4 Bit) | — | **Entfernt** (Header fix) |
| **TOS** (8 Bit) | **Traffic Class** (8 Bit) | Umbenannt |
| — | **Flow Label** (20 Bit) | **Neu** (QoS) |
| **Total Length** (16 Bit) | **Payload Length** (16 Bit) | Nur Nutzdaten |
| **Identification** (16 Bit) | — | → Extension Header |
| **Flags** (3 Bit) | — | → Extension Header |
| **Fragment Offset** (13 Bit) | — | → Extension Header |
| **TTL** (8 Bit) | **Hop Limit** (8 Bit) | Umbenannt |
| **Protocol** (8 Bit) | **Next Header** (8 Bit) | Erweiterbar |
| **Header Checksum** (16 Bit) | — | **Entfernt** |
| **Source Address** (32 Bit) | **Source Address** (128 Bit) | Vergrößert |
| **Destination Address** (32 Bit) | **Destination Address** (128 Bit) | Vergrößert |
| **Options** (variabel) | — | → Extension Headers |

### Entfernte Felder und Begründung

**In IPv6 entfernte Felder:**

**IHL (Internet Header Length)**
  - Header ist jetzt immer 40 Bytes
**Header Checksum**
  - Layer 2 und Layer 4 prüfen bereits
  - Redundant, spart Rechenzeit in Routern
**Fragmentierungsfelder**
  - Nur noch Quell-Host fragmentiert
  - Path MTU Discovery obligatorisch
  - Bei Bedarf: Fragment Extension Header
**Options**
  - Ersetzt durch Extension Headers
  - Flexibler, Router ignorieren unbekannte

### Neue Felder in IPv6

**Flow Label (20 Bit):**
- Kennzeichnet zusammengehörige Pakete
- Ermöglicht schnelles Forwarding ohne Deep Packet Inspection
- Nützlich für QoS, Echtzeit-Anwendungen
- Router kann Pakete eines Flows gleich behandeln

**Next Header (erweiterte Funktion):**
- Zeigt auf nächsten Header (nicht nur Protokoll)
- Ermöglicht Verkettung von Extension Headers
- Flexibler als IPv4 Options

## Fragmentierung: IPv4 vs. IPv6

Ein wesentlicher Unterschied zwischen IPv4 und IPv6 betrifft die Handhabung der Fragmentierung.

### Grundproblem: MTU-Unterschiede

![[mtu-problem.png]]
*<span class="fig-id">03-03-06-mtu-problem</span>: Das MTU-Problem entsteht, wenn ein Paket größer ist als die maximale Übertragungseinheit eines Netzwerksegments.*

### IPv4-Fragmentierung

Bei IPv4 können **sowohl Sender als auch Router** Pakete fragmentieren:

![[ipv4-fragmentierung.png]]
*<span class="fig-id">03-03-06-ipv4-fragmentierung</span>: IPv4-Fragmentierung durch einen Router – das Originalpaket wird in mehrere Fragmente mit gleicher ID aufgeteilt.*

**IPv4-Header-Felder für Fragmentierung:**

| Feld | Bits | Funktion |
|------|------|----------|
| **Identification** | 16 | Eindeutige ID – alle Fragmente eines Pakets haben dieselbe |
| **Flags** | 3 | DF (Don't Fragment), MF (More Fragments), Reserved |
| **Fragment Offset** | 13 | Position des Fragments in 8-Byte-Einheiten |

### IPv6-Fragmentierung

Bei IPv6 fragmentiert **nur der Quell-Host** – Router fragmentieren **nie**:

![[ipv6-fragmentierung.png]]
*<span class="fig-id">03-03-06-ipv6-fragmentierung</span>: IPv6-Fragmentierung mit Path MTU Discovery – nur der Sender fragmentiert, Router senden ICMPv6 "Packet Too Big".*

**IPv6 Fragment Extension Header (Next Header = 44):**

![[ipv6-fragment-extension-header.png]]
*<span class="fig-id">03-03-06-ipv6-fragment-extension-header</span>: Aufbau des IPv6 Fragment Extension Headers mit Next Header, Fragment Offset, M-Flag und Identification.*

| Feld | Bits | Funktion |
|------|------|----------|
| **Next Header** | 8 | Typ des folgenden Headers |
| **Fragment Offset** | 13 | Position in 8-Byte-Einheiten |
| **M (More)** | 1 | Weitere Fragmente folgen |
| **Identification** | 32 | Eindeutige Fragment-ID (größer als IPv4!) |

### Vergleich: IPv4 vs. IPv6 Fragmentierung

| Aspekt | IPv4 | IPv6 |
|--------|------|------|
| **Wer fragmentiert?** | Sender oder Router | Nur Sender |
| **Fragmentierung im Header?** | Ja (3 Felder im Basisheader) | Nein (Extension Header) |
| **Identification-Größe** | 16 Bit | 32 Bit |
| **Minimum MTU** | 576 Bytes | 1280 Bytes |
| **PMTUD** | Optional (aber empfohlen) | Obligatorisch |
| **Router-Verhalten bei zu großem Paket** | Fragmentieren (wenn DF=0) | ICMPv6 "Packet Too Big" |

### Path MTU Discovery (PMTUD)

![[pmtud-ablauf.png]]
*<span class="fig-id">03-03-06-pmtud-ablauf</span>: Path MTU Discovery – der Sender lernt die optimale Paketgröße durch ICMPv6 "Packet Too Big"-Nachrichten.*

### Vorteile der IPv6-Lösung

**Schnellere Router:**
- Keine Fragmentierungslogik in Routern nötig
- Einfacheres Forwarding, höherer Durchsatz

**Weniger Reassembly-Probleme:**
- Fragmente kommen zuverlässiger zusammen an
- Weniger Paketverluste durch fehlende Fragmente

**Bessere Sicherheit:**
- Fragment-basierte Angriffe schwieriger
- Keine "Tiny Fragment"-Attacken auf Router

**Effizientere Nutzung:**
- Sender kennt optimale Paketgröße von Anfang an
- Weniger Overhead durch PMTUD

IPv6 verwendet verkettete Extension Headers statt Optionsfeld:

## IPv6-Adresstypen

### Unicast-Adressen

| Typ | Präfix | Beschreibung |
|-----|--------|--------------|
| **Global Unicast (GUA)** | `2000::/3` (2000:: bis 3fff::) | Weltweit eindeutig und routbar |
| **Link-Local** | `fe80::/10` | Automatisch generiert, nur im lokalen Link gültig |
| **Unique Local (ULA)** | `fc00::/7` (fc00:: bis fdff::) | Entspricht IPv4 privaten Adressen |
| **Loopback** | `::1` | Entspricht 127.0.0.1 bei IPv4 |

### Multicast-Adressen

IPv6 hat **keinen Broadcast** – stattdessen Multicast:

| Adresse | Scope | Beschreibung |
|---------|-------|--------------|
| ff02::1 | Link-Local | Alle Knoten |
| ff02::2 | Link-Local | Alle Router |
| ff02::1:ff00:0/104 | Link-Local | Solicited-Node Multicast |

### Anycast-Adressen

Bei Anycast wird dieselbe Adresse auf mehreren Interfaces konfiguriert – das Paket wird zum "nächsten" (routing-technisch günstigsten) Ziel geliefert:

![[anycast.png]]
*<span class="fig-id">03-03-06-anycast</span>: Anycast-Adressierung – mehrere Server teilen sich eine IP-Adresse, das Routing wählt den nächsten.*

**Eigenschaften:**
- Anycast-Adressen sind syntaktisch identisch mit Unicast-Adressen
- Die Zuordnung erfolgt durch die Routing-Infrastruktur
- Pakete werden immer nur an **einen** Server geliefert (den "nächsten")

**Typische Anwendungsfälle:**
- **DNS-Root-Server** – alle 13 Root-Server-Adressen sind anycast
- **CDN-Endpunkte** – Inhalte vom geografisch nächsten Server
- **DDoS-Mitigation** – Angriffe werden auf viele Standorte verteilt

### Solicited-Node Multicast-Adresse

Die Solicited-Node Multicast-Adresse ist ein zentrales Element des Neighbor Discovery Protocol (NDP) und ersetzt den ineffizienten ARP-Broadcast aus IPv4. Statt alle Hosts im Netzwerk zu stören, wird eine spezielle Multicast-Gruppe gebildet, der nur Hosts mit passenden Adress-Suffixen beitreten.

**Bildung der Adresse:** Jeder Host berechnet aus seiner Unicast-Adresse eine Solicited-Node-Adresse, indem er das feste Präfix `ff02::1:ff` mit den letzten 24 Bit seiner Adresse kombiniert. Bei einer Adresse wie `2001:db8::de12:3456` ergibt sich `ff02::1:ff12:3456`.

![[solicited-node-multicast.png]]
*<span class="fig-id">03-03-06-solicited-node-multicast</span>: Bildung und Funktionsweise der Solicited-Node Multicast-Adresse – nur Hosts mit passenden letzten 24 Bit empfangen die Neighbor Solicitation.*

**Vorteile gegenüber IPv4-ARP:**
- **Kein Broadcast** – Die Anfrage erreicht nicht alle Hosts im Netzwerk
- **Gezielte Zustellung** – Nur Hosts mit passenden letzten 24 Bit empfangen die Nachricht
- **Weniger Störung** – Deutlich reduzierter Overhead, besonders in großen Netzwerken
- **Skalierbarkeit** – Bei 2²⁴ möglichen Gruppen ist die Wahrscheinlichkeit einer Kollision gering

### Übergangs- und Tunneling-Adressen

Die Koexistenz von IPv4 und IPv6 erfordert Mechanismen, die beiden Protokollwelten die Kommunikation ermöglichen. Diese Übergangstechnologien lassen sich in drei Kategorien einteilen:

**1. Dual-Stack:** Beide Protokolle parallel betreiben – der sauberste Ansatz, aber erfordert IPv4- und IPv6-Infrastruktur.

**2. Tunneling:** IPv6-Pakete werden in IPv4-Paketen gekapselt, um IPv4-only-Netze zu überbrücken.

**3. Translation (NAT64):** Protokollübersetzung zwischen IPv6-only und IPv4-only Netzen.

Für diese Mechanismen wurden spezielle Adressbereiche reserviert:

| Typ | Präfix | Beispiel | Verwendung | Status |
|-----|--------|----------|------------|--------|
| **IPv4-mapped IPv6** | `::ffff:0:0/96` | `::ffff:192.0.2.1` | Dual-Stack Sockets – IPv6-Socket kann IPv4-Verbindungen annehmen | Aktiv |
| **NAT64** | `64:ff9b::/96` | `64:ff9b::192.0.2.1` | Ermöglicht IPv6-only Clients Zugriff auf IPv4-Server | Aktiv |
| **Lokales NAT64** | `64:ff9b:1::/48` | `64:ff9b:1::192.0.2.1` | Provider-internes NAT64 | Aktiv |
| **6to4** | `2002::/16` | `2002:c000:0201::/48` | Automatisches Tunneling (IPv4 in Adresse eingebettet) | ⚠️ Deprecated |
| **Teredo** | `2001::/32` | `2001:0:...` | Tunneling durch NAT (enthält Server, Port, Client-IP) | ⚠️ Deprecated |

**IPv4-mapped Adressen** sind besonders wichtig für die Programmierung: Ein Server-Socket, der auf `::` (alle IPv6-Adressen) lauscht, kann auch IPv4-Verbindungen annehmen. Die IPv4-Adresse erscheint dann als `::ffff:x.x.x.x` im Socket.

**NAT64** ist heute die bevorzugte Lösung für IPv6-only-Netze (z.B. Mobilfunk). Der Client sendet an eine synthetische IPv6-Adresse, das NAT64-Gateway übersetzt zu IPv4. DNS64 erzeugt die synthetischen AAAA-Records automatisch.

> [!warning] Veraltete Mechanismen
> **6to4** und **Teredo** gelten als veraltet und sollten nicht mehr verwendet werden. Sicherheitsprobleme (Relay-Angriffe, Spoofing) und unzuverlässige Konnektivität führten zur Abkündigung ([[A-RFC-Index#RFC 7526|RFC 7526]]). Moderne Übergangslösungen sind **Dual-Stack** und **NAT64/DNS64**.

### SLAAC (Stateless Address Autoconfiguration)

SLAAC ermöglicht IPv6-Hosts, sich vollautomatisch eine global routbare Adresse zu konfigurieren – ganz ohne DHCP-Server. Der Router teilt lediglich das Netzwerk-Präfix mit; den Interface Identifier generiert der Host selbst.

**Warum "Stateless"?** Der Router speichert keine Information darüber, welche Adressen vergeben wurden. Jeder Host bildet seine Adresse eigenständig und prüft selbst auf Duplikate.

**Ablauf:**

![[slaac-ablauf.png]]
*<span class="fig-id">03-03-06-slaac-ablauf</span>: SLAAC-Ablauf mit Router Solicitation, Router Advertisement und Duplicate Address Detection (DAD).*

**RA-Flags und ihre Bedeutung:**

| Flag | Name | Bedeutung |
|------|------|-----------|
| **A** | Autonomous | Host darf Adresse per SLAAC bilden |
| **L** | On-Link | Präfix ist direkt erreichbar (kein Router nötig) |
| **M** | Managed | DHCPv6 für Adresse verwenden |
| **O** | Other | DHCPv6 für weitere Infos (DNS, NTP) |

> [!tip] SLAAC + DHCPv6
> In der Praxis wird oft **SLAAC für die Adresse** (A-Flag) kombiniert mit **DHCPv6 für DNS-Server** (O-Flag). Dies nennt man "Stateless DHCPv6".

### Interface Identifier aus MAC-Adresse (EUI-64)

Der EUI-64-Algorithmus wandelt eine 48-Bit MAC-Adresse in einen 64-Bit Interface Identifier um, der für SLAAC verwendet wird.

| Schritt | Aktion | Ergebnis |
|---------|--------|----------|
| 1 | MAC in zwei Hälften teilen | `AA:BB:CC` \| `DD:EE:FF` |
| 2 | `FF:FE` in die Mitte einfügen | `AA:BB:CC:FF:FE:DD:EE:FF` |
| 3 | 7. Bit invertieren (U/L-Bit) | `A8:BB:CC:FF:FE:DD:EE:FF` |

**Beispiel:**
```
MAC-Adresse:  AA:BB:CC:DD:EE:FF
                 ↓
Interface ID: a8bb:ccff:fedd:eeff
```

**Das U/L-Bit (Universal/Local):**
- Bit 7 des ersten Oktetts zeigt an, ob die Adresse global eindeutig (0) oder lokal administriert (1) ist
- Bei EUI-64 wird dieses Bit **invertiert**: Eine global eindeutige MAC (Bit=0) ergibt einen global eindeutigen Interface ID (Bit=1)
- `AA` = `10101010` → invertiere Bit 7 → `10101000` = `A8`

> [!tip] Privacy Extensions
> Aus Datenschutzgründen (MAC-Adresse in IPv6 sichtbar) nutzen moderne Systeme **Privacy Extensions** ([[A-RFC-Index#RFC 4941|RFC 4941]]) mit zufälligen, temporären Interface IDs statt EUI-64.

## NDP - Neighbor Discovery Protocol

NDP ersetzt ARP und weitere IPv4-Protokolle durch ICMPv6-Nachrichten:

| ICMPv6 Type | Name | Funktion |
|-------------|------|----------|
| 133 | Router Solicitation | Router suchen |
| 134 | Router Advertisement | Router kündigt sich an |
| 135 | Neighbor Solicitation | MAC-Auflösung (wie ARP) |
| 136 | Neighbor Advertisement | Antwort mit MAC |
| 137 | Redirect | Besseren Router empfehlen |

### Neighbor Solicitation / Advertisement (MAC-Auflösung)

Neighbor Solicitation (NS) und Neighbor Advertisement (NA) sind das IPv6-Äquivalent zu ARP. Wenn ein Host die MAC-Adresse eines Nachbarn benötigt, sendet er eine NS-Anfrage und erhält eine NA-Antwort.

**Wichtiger Unterschied zu ARP:** Statt eines Broadcasts an alle Hosts im Segment nutzt NDP eine Solicited-Node Multicast-Adresse. Dadurch werden nur Hosts gestört, deren IPv6-Adresse auf die gleichen 24 Bit endet.

![[ndp-neighbor-discovery.png]]
*<span class="fig-id">03-03-06-ndp-neighbor-discovery</span>: NDP Neighbor Discovery – Ablauf der MAC-Adressauflösung mit Neighbor Solicitation und Advertisement.*

**Neighbor Cache States:**

| Status | Bedeutung |
|--------|-----------|
| **INCOMPLETE** | NS gesendet, warte auf NA |
| **REACHABLE** | Kürzlich bestätigt erreichbar |
| **STALE** | Eintrag veraltet, bei Nutzung neu prüfen |
| **DELAY** | Warte kurz, bevor NS gesendet wird |
| **PROBE** | Sende NS zur Erreichbarkeitsprüfung |

> [!info] Neighbor Cache anzeigen
> ```bash
> # Linux
> ip -6 neigh show
> 
> # Windows
> netsh interface ipv6 show neighbors
> ```

## IPv6-Übergangsmechanismen

### Dual-Stack

Dual-Stack ist der sauberste Übergangsmechanismus: Ein Host betreibt IPv4 und IPv6 gleichzeitig und kann mit beiden Protokollwelten kommunizieren.

![[dual-stack.png]]
*<span class="fig-id">03-03-06-dual-stack</span>: Dual-Stack Host mit parallelen IPv4- und IPv6-Stacks – kann mit beiden Protokollwelten kommunizieren.*

**Happy Eyeballs (RFC 8305):** Moderne Betriebssysteme und Browser nutzen diesen Algorithmus, um IPv6 und IPv4 parallel zu versuchen und die schnellere Verbindung zu verwenden. Das vermeidet Wartezeiten, wenn ein Protokoll nicht funktioniert.

**Voraussetzungen:**
- ISP muss IPv6 bereitstellen (natives IPv6 oder Tunnel)
- Router und Firewall müssen IPv6 unterstützen
- DNS muss A- und AAAA-Records auflösen können

### Tunneling (6in4)

Tunneling kapselt IPv6-Pakete in IPv4-Paketen, um IPv6-Inseln über ein IPv4-only-Netzwerk zu verbinden. Der IPv4-Header verwendet Protocol 41 zur Kennzeichnung des gekapselten IPv6-Pakets.

![[6in4-tunnel.png]]
*<span class="fig-id">03-03-06-6in4-tunnel</span>: 6in4 Tunneling – IPv6-Pakete werden in IPv4 gekapselt und zwischen Tunnel-Endpunkten transportiert.*

**Konfigurationsbeispiel (Linux):**
```bash
# Tunnel erstellen
ip tunnel add tun6to4 mode sit remote 198.51.100.1 local 203.0.113.1
ip link set tun6to4 up
ip -6 addr add 2001:db8:a::1/64 dev tun6to4
ip -6 route add 2001:db8:b::/48 dev tun6to4
```

> [!warning] Tunnel-Broker
> Für Heimanwender ohne natives IPv6 bieten Tunnel-Broker wie **Hurricane Electric** (tunnelbroker.net) kostenlose 6in4-Tunnel an.

### NAT64/DNS64

NAT64 und DNS64 ermöglichen es IPv6-only Clients, mit IPv4-only Servern zu kommunizieren. Dies ist besonders wichtig für Mobilfunknetze und Cloud-Umgebungen, die keine IPv4-Adressen mehr für jeden Client vergeben können.

![[nat64-dns64.png]]
*<span class="fig-id">03-03-06-nat64-dns64</span>: NAT64/DNS64 Architektur – IPv6-only Client erreicht IPv4-Server durch Protokollübersetzung.*

**Zusammenspiel DNS64 + NAT64:**
1. **DNS64** synthetisiert AAAA-Records für IPv4-only Ziele (Präfix `64:ff9b::/96` + IPv4-Adresse)
2. **NAT64** übersetzt die IPv6-Pakete in IPv4 und umgekehrt

**Einschränkungen:**
- Funktioniert nicht mit eingebetteten IPv4-Adressen (z.B. in SIP, FTP)
- Literal IPv4-Adressen im Browser funktionieren nicht
- Erfordert IPv6-fähige Anwendungen

> [!tip] NAT64 testen
> Viele Mobilfunknetze nutzen bereits NAT64. Zum Testen: WLAN deaktivieren und prüfen, ob IPv4-only Websites erreichbar sind.
